## 2. 议题 A：新版导向标识设计器

### 2.1 他们现在的路线（发布会口径，2026-08-15）

- 之前"为什么设计器这么久没更新"的答案是：**等地图完全重写、接入数据库之后再做同样的升级**。
- 升级方向：**新增"导入车站"直连地图数据库**，左侧线路列表与地图数据实时同步；标志色、中英文站名、起终点、下一站全部一键加载，不用手打。
- 新增"**进站 / 乘车 / 出站**"三条流程，并指定牌面出现位置（楼梯 / 无障碍 / 乘车方向 / 卫生间 / 出口）。
- 现场演示：18 号线文华路站"乘车方向"；22 号线定福庄站站名牌（下一站甘露园）。
- 画布能力：图标素材搜索（1–40 号线徽标可拖入）、自动尺寸、单层 10 倍、双模块、分组、清空、一键复制。
- **后续愿景：一键生成一条线路全部车站的不同款式导向牌。**

👉 我的判断：**他们正从"手工作图工具"变成"数据库驱动的批量生产工具"**。这个方向和雨城通刚好是互补的——他们做"设计 + 数据源"，我们做"批量落地 + 发布"。今晚要把这句话说出来。

### 2.2 我方现状（一句话 + 一张表）

> **一句话**：雨城通是目前已知最完整的 NaL v2 第三方读取器——三个工具、8 种元素、19 种降级规则、104 条回归断言，全部有代码与测试。

| 维度       | 我方实现                                                                                                               |
| ---------- | ---------------------------------------------------------------------------------------------------------------------- |
| 支持的工具 | `nalvitool`（导向标志，v1 + v2）、`nalwall`（墙面标志，仅 v2）、`nalstasign`（站名站牌，v1 + v2）                      |
| 支持的元素 | `asset` / `text` / `ribbonText` / `exit` / `tinted` / `lineBadge` / `column` / `customSvg`（跳过）                     |
| 素材号映射 | `way@` / `stn@` / `oth@` / `sub@` / `line@` / `clss@` / `cls@` 七段全部建表                                            |
| 校验       | 一次性收集全部问题（上限 40），路径精确到 `boards[0].rows[1].groups[0].elements[3].color`，最多展示 8 条 + "其余 N 处" |
| 版本闸门   | `schemaVersion > 2` **整份拒绝**并提示升级                                                                             |
| 降级       | 主题 C/D → A/B 底色；自动尺寸 → 8 格；双画板/双模块只导第一组；`column` 摊平；旋转忽略；墙面 `scale 2/3` 压成单层      |
| 回归       | `pnpm metro:check`：22 组 / 104 条断言，含"禁止从素材号抠线路号"的回归锁                                               |

### 2.3 真正的风险：我们是"硬校验"，升版即全拒

| v3 可能的变化                          | 对我方的后果                                  |
| -------------------------------------- | --------------------------------------------- |
| `schemaVersion` → 3                    | **全量拒绝**（提示清楚，但零导入）            |
| 新增/重命名元素 `kind`                 | **全量拒绝**（未知 kind 直接抛出）            |
| 素材引用改成 ID / hash / URL / PNG     | **全量拒绝** + 所有语义映射失效（**最致命**） |
| 颜色改成 `rgb()` / 8 位 hex / 带 alpha | **全量拒绝**（只收 `#RRGGBB`）                |
| `canvas.length` 出现 11 或小数         | **全量拒绝**（白名单 `{4,5,6,7,8,9,10,12}`）  |
| 新增可选字段、保留现有形状             | **安全**（未知字段被忽略）                    |
| 新增素材号（`way@31+`）                | 不炸，但**静默丢内容**（只告警）              |

**我要传递的态度**：不是"你们别改"，而是"**改可以，请给迁移期和新旧并行**"。我方对策已经在想：双解析器 + `wayfinding-ir` 中间层 + 版本 registry；但那是成本，能省则省。

### 2.4 如果对方问"你希望新版长什么样"——10 条需求（按优先级）

**P0（不做我会很痛）**

1. **格式契约化**：公开 `docs/json-format-v2.md` 为稳定规范，附 **JSON Schema + CHANGELOG + 迁移脚本**。
2. **版本协商**：`schemaVersion` 之外给 `minReaderVersion` 或兼容标记，让旧读取器能说"你需要升级"，而不是"这不是有效文件"。
3. **素材 manifest**：素材仍按裸 `.svg` 文件名引用，号段只增不改，并提供**带 hash 的素材清单**（我现在只能靠样例反推 `clss@20` = 22 号线）。
4. **主题解析值**：theme A–D 之外，导出附 `theme.resolved`（底色/前景色），别让读取器硬编码你们的调色板。
5. **批量导出**：整线导出时，一次给**多个牌面**（而不是让我模拟点 20 次），并保留稳定的文件命名与顺序。

**P1（有更好）**

6. **程序化导出**：headless / Node API / CLI 任一，能批量转换。
7. **外部数据源**："导入车站"目前连你们的库；若能吃外部 JSON/CSV，雨城通愿意第一个接。
8. **离线可复现**：导出文件内联字体/素材快照（`assets` 已在做，保持），保证三年后还能打开。
9. **多画板语义明确**：`boards` 是 A/B 面还是同面多模块？>2 时怎么办？v3 里建议改名 `surfaces` 并写清楚。
10. **安全边界写清**：`customSvg` 的快照规则、允许的元素白名单——我们这边受限 SVG 禁 `script`/`foreignObject`/`image`/`use`，需要知道你们的边界。

### 2.5 必问的 10 个技术问题（按顺序问，问完打勾）

- [ ] 1. v3 是否保留 `elements` **扁平数组 + `kind` 判别**？现有 8 种 kind 原样可读吗？新能力是加枚举还是重构？
- [ ] 2. `type` 仍是否 `nalvitool/nalwall/nalstasign`？会不会加 `minReaderVersion`？
- [ ] 3. 能否公开格式文档 + JSON Schema + CHANGELOG + 迁移脚本？
- [ ] 4. theme C/D 的**授权与降级规则**是什么？（我们现在按 NaL 规则落到 A/B 底色，这是猜的）
- [ ] 5. 素材号还稳定吗？会不会改成 ID/hash？能发 manifest 吗？
- [ ] 6. `canvas.length` 取值域会不会扩（现在 4–12 不含 11）？自动尺寸时能不能直接输出解析后的实际长度？
- [ ] 7. `boards` 多画板的语义？（A/B 面 vs 多模块）
- [ ] 8. 旋转/变换只保留 flip + 90° 步进吗？任意角度、缩放、透明度走新字段还是复用 `transform`？
- [ ] 9. `customSvg` 快照还在同一 JSON 的 `assets`（`mime` + `content`）吗？会不会外链/压缩包？
- [ ] 10. `staline`（线路通长）是独立 `type` 还是 `nalvitool` 内新元素？能降级成 `column`/`lineBadge` 吗？

### 2.6 希望他们写进文档的 6 条承诺（能拿到 3 条就够）

1. v2 再保留**至少两个大版本**，设计器支持"另存为 v2"。
2. 现有 8 种 `kind` 的**名称与字段语义不可复用、不可重命名**。
3. 素材以**裸 `.svg` 文件名**引用，号段只增不改，发 **manifest**。
4. 颜色仍为 `#RRGGBB`，透明度/渐变**另立新字段**。
5. `canvas` 保持 `{rows: 1|2, length}`，自动尺寸**附带解析后的实际长度**。
6. 未知字段继续**忽略**（这条你们做得很好，请写进契约）。

### 3.4 三条具体反馈（这是他们要的"积极反馈"，比夸奖值钱）

1. **缺 JSON Schema**：文档约定"可选字段取默认值时不写出"，这很好；但第三方只能靠样例反推结构，一个字段猜错就是整份拒绝。建议发 Schema。
2. **theme C/D 的授权规则不透明**：文件里只有字母，没有解析后的颜色，读取器只能硬编码你们的调色板；换个主题就错色。建议导出带 `theme.resolved`。
3. **素材号是入库流水号，不是语义**：`clss@20` 是 22 号线、`line@24` 是亦庄线——第三方几乎必然误读。我们专门写了回归锁禁止"从号段抠线路号"。建议发带 hash 的 manifest。

> 说完补一句："这三条我这边都踩过，可以整理成 issue 发你们。"

### 3.5 可以主动抛的两个合作点

1. **"你们做设计，我们做量产"**：整线批量导出出来后，我们这边可以做**批量导入 + 批量出图 + 打印排版 + 分享/审核**。他们发布会说"一键生成一条线路全部车站"，那**生成之后谁来发**？这正是我们的位置。
2. **"我们做你们第一个外部数据源"**：如果"导入车站"未来开放外部 JSON/CSV，雨城通可以把临东线网按你们的模型导出（站点、中英文名、线路色、起终点、下一站、设施、出入口），帮你们验证"非北京数据"的兼容性。

### 3.6 雨城通的边界（别越界承诺）

- 不做通用设计器、不做商业授权、不做他们的数据转售。
- 不承诺"v3 一周内支持"——老实说分档：**枚举/字段级 1–2 天；结构调整 1–2 周；重构级 1 个月起**。
- 不承诺用户量、增长、留存这类拿不出的数字。
